# 計測プラン（利用状況の記録。2026-11-24 決定）

## 目的

1. どの機能を、どの順番で使っているか
2. どこでつまずいているか（エラー、失敗、待ち時間、許可を断ったところ）
3. どの画面・操作のあとで閉じることが多いか。特に、初回起動から主な機能（方角ガイド、「見えた」の答え）までのどこで離れるか

## 決めたこと（tsuchida さん、2026-11-24）

- ツールは Firebase Analytics と Firebase Crashlytics。PostHog などは使わない（今の構成にそのまま足せて無料。データを預ける先を増やさない）。
- 2.0.1（ビルド 15）に、英語対応と一緒に入れる（ブランチ `analytics`、`l10n-english` から分岐）。
- 計測をオフにするボタンは作らない。電気通信事業法の外部送信規律は、プライバシーポリシーでの公表で満たす。App Store も、トラッキングをしないので許可（ATT）は要らない。
- 個人情報は送らない。送るのは決まった値（選択肢）と数字だけ。地名・場所の名前・入力した文・緯度経度は送らない。Firebase のユーザー ID は設定しない（端末ごとの匿名の ID だけ）。

## しくみ

- 窓口は `lib/services/analytics/analytics_service.dart` の1か所。イベント名とパラメータはここだけに書く。ツールを変えるときは `AnalyticsBackend` を実装し直す。
- 画面の表示は `lib/services/analytics/analytics_route_observer.dart` が、名前の付いた画面とシート（`RouteSettings.name`）の行き来を見て送る。戻る操作で戻った先も送る。名前は `AppRoutes` と各シートの `show` で付ける。最初の画面は `MyApp` が `AnalyticsService.rootScreen` に入れる。
- 送るのに失敗しても例外は出さない。`init` の前とテストでは何もしない。
- 開発中のデータと本番を分ける: デバッグ版は送らない。ネイティブの設定（iOS の Info.plist の `FIREBASE_ANALYTICS_COLLECTION_ENABLED` と `FirebaseCrashlyticsCollectionEnabled`、Android の AndroidManifest の `firebase_analytics_collection_enabled` と `firebase_crashlytics_collection_enabled`）で最初から止めておき、リリース版だけ `AnalyticsService.init` でオンにする。TestFlight の版は本番と同じ作りなので、利用者の属性 `channel`（production / testflight）で分ける（iOS は購入の記録のファイル名が sandboxReceipt かで見分ける。Android はいまは production だけ）。
- 落ちたときの記録: リリース版で、Dart の例外と Flutter の描画の例外を Crashlytics に送る。iOS は、リリース版のビルドのときに記号の情報（dSYM）を上げる処理を Xcode のプロジェクトに足した（「Crashlytics: upload symbols」）。最後に見ていた画面を `last_screen` として付ける。

## 画面の名前（screen_view の screen_name）

intro_1、intro_2、intro_3（使い方）、welcome（許可のお願い）、home、finder（方角ガイド）、settings、places、record、plus、data_source、intro_from_settings（設定から開いた使い方）、sheet_whats_new、sheet_always、sheet_quiet_hours、sheet_add_place、sheet_nationwide、sheet_calibrate

## イベントの一覧

画面
- `screen_view`（Firebase の標準）: 画面やシートが出たとき、戻る操作で戻ったとき。`screen_name`。どの画面をどの順番で見たか。
- `home_state_shown`: ホームの状態が変わったとき。`state`（clouds / empty / night / offline / no_permission）。開いたときに雲が見えていた割合、許可のないままの人の割合。

初回起動から主な機能まで
- `first_open`（標準）: 初めて開いた。
- `permission_prompt_shown`: 許可のお願いを出す直前。`kind`（location / notification / location_always）。
- `permission_result`: 許可の結果。`kind`、`result`（granted / denied）。どの許可で断られているか。
- `onboarding_completed`: Welcome を終えてホームに進んだ。
- `notification_opened`: 通知を押して開いた。`via`（tap）。通知のボタンで答えたものは `cloud_report` の `source` が notification_button になる。
- `finder_opened`: 方角ガイドを開いた。`source`（home / notification）。
- `finder_aligned`: 開いてから最初に向きが合った。`seconds`。手間取っているか。
- `cloud_report`: 「見えた/見えなかった」を答えた。`answer`（seen / not_seen）、`source`（reports と同じ値）。

設定と場所
- `notify_toggled`（`enabled`: 1 / 0）、`range_changed`（`km`）、`quiet_hours_changed`、`place_added`（`place_count`）、`place_removed`（`place_count`）、`nationwide_opened`（`count`）

Plus
- `plus_viewed`: Plus の画面を開いた。`source`（settings_manage / settings_banner / settings_range / home_add_place / places_note）。
- `purchase_started`（`product`: monthly / lifetime）、`purchase_result`（`product`、`result`: success / cancelled / failed / pending）、`restore_result`（`result`: success / not_found / failed）

つまずき
- `error_shown`: `kind`（location_unavailable / network / sky_load_failed / geocode_failed / compass_unavailable / purchase_failed）。種類だけで、エラーの文は送らない。
- `calibrate_shown`: 方位の調整を出した。
- `sky_loaded`: 雲の一覧がサーバーから届いた（または失敗した）。`duration_ms`、`result`（ok / failed）。
- 同じ操作の繰り返しと戻る操作は、`screen_view` の並びを「経路データ探索」で見る（専用のイベントは作らない）。

離脱
- `app_background`: アプリが裏に回った。`last_screen`、`last_action`（直前に送ったイベント名）、`session_seconds`。

利用者の属性（ユーザー プロパティ）
- `is_plus`（yes / no）、`lang`（ja / en）、`place_count`、`channel`（production / testflight）

## Firebase と GA4 の設定（tsuchida さんにお願いすること）

1. Firebase コンソール > プロジェクトの設定 > 統合 > Google アナリティクスを有効にする（GA4 のプロパティとつなぐ）。つながっていないと、イベントが届かない。
2. Firebase コンソール > Crashlytics を開いて「有効にする」。
3. GA4 > 管理 > データの収集と修正 > データ保持 を「14 か月」にする（初期値は2か月で、ファネルや経路の探索で古いデータが見えなくなる）。
4. GA4 > 管理 > データの収集と修正 > データ収集 で、Google シグナルはオフのままにする。「詳細な位置情報とデバイスデータの収集」はオフにする（国や地域までにする。プライバシーポリシーの「おおまかな地域」と合わせる）。
5. ユーザー プロパティ（is_plus、lang、place_count、channel）と、よく使うパラメータ（screen_name 以外の state、kind、result、source、answer、last_screen、last_action）を、GA4 > 管理 > カスタム定義 で「カスタム ディメンション」に登録する。登録しないと、レポートの画面で値ごとに分けて見られない（登録より前のデータには付かないので、公開の前に済ませる）。

## イベントが届いていることを確かめる手順

- デバッグ版は送らない作りなので、確かめるときは「リリース版を DebugView に出す」方法を使う。
- iOS（Mac から）: `ios/Runner.xcworkspace` を Xcode で開き、Product > Scheme > Edit Scheme > Run で、Build Configuration を Release にし、Arguments Passed On Launch に `-FIRDebugEnabled` を足して、iPhone に Run する（確かめ終わったら、Debug に戻して引数を消す。スキームの変更はコミットしない）。
- TestFlight の版で見るときは、DebugView には出ない。GA4 の「リアルタイム」のレポートに、数分おくれて出る。
- Android: `adb shell setprop debug.firebase.analytics.app com.tsuchida.thundercloud` のあと、リリース版を入れて開く。終わったら `adb shell setprop debug.firebase.analytics.app .none.`。
- Firebase コンソール > Analytics > DebugView で、画面を開くたびに `screen_view`、方角ガイドで `finder_opened` → `finder_aligned`、ホームに戻って裏に回すと `app_background` が並ぶことを見る。
- Crashlytics は、リリース版で一度アプリを落とすと、次に開いたときに届く（確かめるときだけ、デバッグ用の画面で `FirebaseCrashlytics.instance.crash()` を呼ぶ。コードには残さない）。

## 見るためのレポートの作り方（GA4 > 探索）

初回起動から主な機能までのファネル（目標到達プロセス データ探索）
- 手順: first_open → screen_view（screen_name = welcome）→ permission_result（kind = location、result = granted）→ onboarding_completed → home_state_shown → finder_opened → cloud_report
- 「オープン ファネル」をオフ、「経過時間を表示」をオンにする。内訳に `channel` を入れて testflight を外す（フィルタ: channel = production）。
- 段ごとの離脱数が出る。許可で落ちているか、雲がなくて方角ガイドまで行かないのかが分かる。

通知から答えるまでのファネル
- notification_opened → finder_opened（source = notification）→ finder_aligned → cloud_report
- 通知を送った数はサーバーの `notification_log`（Firestore）にあるので、日ごとの送った数と `notification_opened` の数を並べて、開かれた割合を見る（GA4 には出ない）。

離脱が多い画面
- 自由形式で、行に `last_screen`、値に `app_background` のイベント数。次に `last_action` を行に足すと、どの操作のあとで閉じたかが分かる。
- 経路データ探索で、始点を `first_open` にすると、初回の人がどの画面を通ってどこで終わったかが木の形で見える。

つまずきが多い操作
- 自由形式で、行に `error_shown` の `kind`、値にイベント数とユーザー数。`permission_result` の `result = denied` を `kind` ごとに。`purchase_result` を `result` ごとに。
- 待ち時間は `sky_loaded` の `duration_ms` の平均と分布（`result` ごと）。
- 方角ガイドの手間は `finder_aligned` の `seconds`。

## App Store の「アプリのプライバシー」に足すもの

今の申告（docs/ストア提出メモ.md の3）に、次を足す。どれも「トラッキングに使用しない」。

- 使用状況データ > 製品の操作: 目的は「アナリティクス」。ユーザに関連付けない（Firebase のユーザー ID を設定しないため）。
- 診断 > クラッシュデータ: 目的は「App の機能」（不具合を直すため）。ユーザに関連付けない。
- 診断 > パフォーマンスデータ: 読み込みの時間。目的は「アナリティクス」。ユーザに関連付けない。
- 識別子 > デバイス ID: Firebase がつくる端末ごとの ID（App インスタンス ID）。目的は「アナリティクス」。ユーザに関連付けない。
- 位置情報 > おおよその場所: IP アドレスから Google が推定する地域。目的は「アナリティクス」。ユーザに関連付けない。

Google Play（データ セーフティ）も同じく、「アプリのアクティビティ（アプリの操作）」「アプリの情報とパフォーマンス（クラッシュログ、診断）」「デバイスやその他の ID」「おおよその位置情報」を、目的「分析」で足す（Android を出すとき）。
