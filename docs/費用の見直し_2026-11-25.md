# 費用の見直し（2026-11-25）

Google Cloud（Firebase の Blaze）の費用を減らすための分析と、やったこと。

## 費用の推移

- Firebase の「使用量と請求額」（入道雲サーチのプロジェクトだけ）: 2026年9月 ¥1,211、10月 ¥736。
- 11月（11/24 まで）: 使用費用 ¥393 から、無料枠などの割引 -¥232 を引いて、請求額 ¥161（Google Cloud の「お支払い > レポート」。請求先アカウントには ほかに future-seeds-app と kenkyu-502004 がつながっているが、費用がかかっているのは入道雲サーチだけ）。
- 11月の請求額の予想（グラフの灰色）は ¥451 だが、雲の多い日が続く前提で高めに出ている。実際の着地は ¥250〜450 くらいと見ていた。

- Cloud Run の通信量: ¥3
- そのほか（Cloud Run のメモリ・CPU、ログ、保存、イメージの保管など）は、無料枠と割引（-¥232）に収まって ¥0。

## やったこと

1. v1 の関数 9 つを本番から削除した（2026-11-25、tsuchida さんの指示）。`cacheWeatherData`、`checkThunderClouds`（asia-northeast1）、`cleanupExpiredLikes`、`cleanupExpiredPhotos`、`cleanupWeatherCache`、`getCacheStats`、`getDirectionalWeatherData`、`getWeatherData`、`monitorThunderClouds`（us-central1）。定期実行が約9.75個から 4 個になり、Cloud Scheduler の請求が ¥72（24日分）から月 ¥15 ほどになる見込み。1.0.4 を使っていた人は、7日以内に開いた人が 0 人、30日以内が 1 人だった。
2. `cleanupExpiredPhotos` を `index.js` からも外した（全部まとめてデプロイしたときに復活しないように）。
3. （2026-11-25、案A。「デプロイして」で `updateNowcastClouds` をデプロイ済み。05:26 UTC の版。その後の実行は、続き・新規・終了のどの場合も、エラーなしで通知の判定が動いた）5分ごとの処理で、雲の一覧の読み取りを 2 回から 1 回にした。
   - 雲の保存（`NowcastService._saveClouds`）が、書いた直後の「見えている雲」を返し、通知の判定（`CloudWatchService.run` の `visibleClouds`）がそれを使う。今までは、書いたあとにもう一度 `status == active` の雲をすべて読んでいた。追っている雲は必ず「続き・新規・見えない・終了」のどれか 1 つになるので、書いた直後の見えている雲は「続き」と「新規」だけで、読み直した結果と同じになる（テストで確かめた）。
   - すでに見えなくした雲（`isVisible: false`）を、毎回書き直さないようにした（書き直しても変わるのは `updatedAt` だけで、どこからも読まれない）。
   - 通知の判定、アプリに出る雲の位置、通知の内容は変わらない。

4. （2026-11-25、デプロイ済み。「`cleanupOldClouds` をデプロイして、`cleanupInactiveMembers` を削除して」で、08:17 UTC に `cleanupOldClouds` をデプロイし、そのあと `cleanupInactiveMembers` を削除した。本番の関数は5つ、定期実行は3つ）毎日の片付け 2 つを 1 つの定期実行にまとめた。`cleanupInactiveMembers`（毎日 4:00、1年開いていない人の削除）を `cleanupOldClouds`（毎日 3:30）の中で続けて行う形にして、`index.js` から外した。定期実行が 3 個になり、Cloud Scheduler の請求が 0 円になる見込み（ほかのプロジェクトが無料の 3 個を使っていなければ。月 ¥15 ほどの節約）。タイムアウトは 300 秒にした。どれか 1 つが失敗しても、残りは続ける。先に新しい版を入れてから旧関数を消したので、削除は1日も途切れない。2026-11-26 3:30（日本時間）の実行のログで、4つの処理が動いたかを確かめる。

## 費用が増える仕組み（今後の参考）

- Firestore の読み書きは、雲が多い日に大きく増える（静かな日は読み取り約2万回・書き込み約3千回、雲の多い日は読み取り約19万回・書き込み約9万回）。
- 5分ごとに、追っている雲のすべての記録を、変わっていなくても書き直している（位置・ふち・時刻が毎回変わるため）。
- アプリは雲の一覧を購読しているので、雲の記録が書き換わるたびに、開いている端末ごとに 1 回ずつ読み取りが数えられる。利用者が増えると、ここが大きくなる。

## まだ残っている案（効果と使用感への影響）

- 案B: 変わっていない雲は書き直さない。位置が約1km動くか、形が変わったときだけ書き、そうでなければ「最後に見た時刻」を15分に1回だけ更新する。書き込みが半分以下になる見込み。ただし、アプリに出る雲の位置が最大で15分ほど古いままになることがある。
- `recordAirportObservations`（30分ごと、検知の見直し用のデータ集め）をやめる。効果は小さい。
