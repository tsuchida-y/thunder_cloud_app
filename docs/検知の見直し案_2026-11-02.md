# 検知の見直し案（2026-11-02）

tsuchida さんが何日か使って、「出ていないのに『入道雲が現れました』と通知が来ることが多い。とくに曇りの日。見たいのは、青空にそびえる大きな入道雲」と気づいたことを受けて、本番のデータを調べて、直し方をまとめた。まだ何も変えていない。どれを入れるかは tsuchida さんに決めてもらう。

法律と規約の決まり（CLAUDE.md）は守る。どの案も、予想ではなく、いまの観測から読み取るだけにしてある。

## 1. 見えなかった4つの雲を調べた

あなたが「見えなかった」と答えた4つの通知（reports）と、その雲（clouds）を突き合わせた。

- 10/30 15:10 通知（雲 P9ULWG…）: 方角 269°（西）、距離 72km、てっぺん -47℃（高さの見積もり 9.4km）、広さ 3.5km²（1ピクセル）
- 10/30 15:55 通知（雲 ouW9Gr…）: 方角 267°、距離 86km、てっぺん -23℃（6km）、広さ 32km²
- 10/30 16:40 ホームの表示（雲 0QYsxr…）: 方角 289°、距離 83km、てっぺん -38℃（7.9km）、広さ 18km²
- 11/02 08:30 通知（雲 WmDDOy…）: 方角 261°、距離 80km、てっぺん -37℃（7.2km）、広さ 7km²

共通点は4つ。

1. **どれも遠い**。72〜86km。方角はどれも西で、日本海の上や秋田の海ぞい。
2. **どれも小さい**。1〜9ピクセル（約 3.5〜32km²）。冬の日本海側に出る、小さなしゅう雨の雲。雷の活動度はどれも0。
3. **どれも、太陽が低い時間に通知が出ていた**（下の2）。
4. てっぺんは -23〜-47℃。冬は地上の気温が低いので、同じ温度でも夏より低い雲（6〜9km）。

## 2. 原因

### 原因1: 一面の曇りの判定が、太陽が低いと止まる（いちばん大きい）

いまの「一面の曇りか」の判定（アメダスの日照時間）は、「いまも1時間前も、太陽が15°より高いとき」だけ働く（`AMEDAS.SUNSHINE_MIN_SUN_ALTITUDE_DEG: 15`、sky_observations.js の `isOvercast`）。岩手では次のとおり。

- 7月20日: 通知できる15.7時間のうち、判定が効くのは10.7時間。効かない時間は 32%
- 10月30日・11月2日: 通知できる11.5時間のうち、判定が効くのは 08:40〜15:10 の6.5時間だけ。効かない時間は **43%**
- 12月21日: 判定が効くのは 09:50〜14:30 の4.7時間。効かない時間は **55%**

見えなかった3回の通知（10/30 15:10、15:55、11/02 08:30）は、**どれも判定が止まっている時間に出ていた**。曇りの日に出る、という実感の原因はこれだと思う。実際のアメダスで確かめた（見張る場所から20km以内の地点）。

- 10/30 15:10: 太陽は 14.2°（基準の15°に0.8°足りない）。20km以内で日照が取れた5地点が、どれも直前10分も前の1時間も日照0。
- 10/30 15:55: 太陽は 7.5°（1時間前は 17°）。同じく5地点とも日照0。
- 11/02 08:30: 太陽は 22.8°（1時間前が 14° で、「1時間前も15°より高い」を満たさなかった）。同じく5地点とも日照0。

つまり、**3回とも、近くのアメダスは「一面の曇り」と言っていた**。判定の条件がわずかに合わず、止まっていただけ。

15° が高すぎることも、アメダスの実測で確かめた。11月1日の 06:30〜17:00 の全国のデータで、太陽の高さごとに、10分間に日差しがあった地点の割合を見た。

- 太陽 0〜3°: 4%（59/1,319地点）
- 3〜6°: 24%
- 6〜9°: 33%（朝7:00 のように晴れた地域が多い時刻は 44%）
- 9〜12°: 38%
- 12〜15°: 49%
- 15〜20°: 68%
- 20°以上: 83%

太陽が6°あれば、日照計は晴れた場所で反応する。15° まで待つ必要はない。

### 原因2: 遠すぎる雲も知らせている

プラスの範囲は90km。60kmより遠い雲は「見えるかもしれません」として通知している（`MAYBE_VISIBLE_KM: 60`）。てっぺんが 7〜9km の雲を 80km 先から見ると、見上げる角度は 4〜7° で、水平線のすぐ上の小さなふくらみになる。山、建物、もやで、まず見えない。

雲のてっぺんの見上げる角度（地球の丸みを引いた値）を計算した。

- 見えなかった4つ: 7.1°（9.4km、72km）、3.6°（6km、86km）、5.1°（7.9km、83km）、4.8°（7.2km、80km）。どれも8°未満。
- 「見上げる角度が8°以上」になる、いちばん遠い距離: 高さ6kmなら42km、8kmなら55km、10kmなら69km、12kmなら82km、14kmなら95km。

つまり、背が高い雲ほど遠くからでも見える。8°を目安にすると、背の低い雲や遠い雲は自然に外れ、夏の背の高い雷雲は80km 先まで残る。

### 原因3: 「背の高い雲」の線が甘い

いまは、てっぺんが -20℃ より冷たければ入道雲とする。ところが、本番の雲4,751個のてっぺんの温度は、中央値が -30℃、-30〜-20℃ の雲が 2,304個（約半分）。-20℃ は、冬だと高さ4kmほどの雲でも超えてしまう。背の高い夏の雷雲は -50℃ より冷たくなることが多い（docs/検知の精度を上げるデータの比較.md の沖縄の例では -60〜-80℃）ので、写真のような雲とは違う。

また、高さの見積もりは 6km 未満を 6km に切り上げる（`MIN_TOP_KM: 6`）。ので、実際より高く表示される雲がある（10/30 15:55 の雲は -23℃ で、地上の気温を6℃くらいとすると見積もりは約4.5kmだが、6km と出ていた）。

### 参考: 赤外画像で曇りを判定する案は、よくなかった

太陽が低くても使えるように、ひまわりの赤外画像（赤外の温度と、地上の気温の差）で「空が曇っているか」を判定できないか調べた。昼のアメダスの日照と比べると、曇り（日照0）の98%は見つけられたが、晴れ（日照あり）の30〜43%も曇りと間違えた。薄い雲や、まばらな雲を拾うため。曇りの判定には使わず、アメダスの日照を主役にする。

## 3. 変更案（効く順）

### 案A: 一面の曇りの判定を、太陽が低くても働かせる

- 太陽の高さのしきい値を 15° から **10°** に下げる。全国の実測では、6°あれば日照計は晴れた場所で反応する。ただし岩手の晴れた日のデータでは、夕方に太陽が 6〜8° まで下がると、晴れていても近くの地点の日照が 0〜2/5 になった（西の山に太陽が隠れるためと考えられる）。そのため、7° ではなく、余裕をみて 10° にする。
- 「いまも1時間前も」ではなく、**前の1時間のうち、太陽が10°以上だった時間が30分以上あれば判定する**。見えなかった3回の通知は、新しい条件でも、3回とも判定できる（10/30 15:10 は1時間ずっと10°以上、15:55 は約45分、11/02 08:30 は1時間ずっと）。
- 判定できない時間（前の1時間のほとんどで、太陽が10°より低い。日の出の直後と、日没の直前）は、**通知を送らない**（見えるかどうか確かめられないので、安全側に倒す）。アプリのホームでは見られる。
- 効く場面: 見えなかった3回の通知は、近くのアメダス5地点がどこも日照0だったので、新しい条件で**3回とも「一面の曇り」として外れる**。
- 副作用: 日の出の直後と日没の直前の、低い太陽に照らされた入道雲の通知が、日照を確かめられなくて減る。夕方は夏の入道雲の見どころでもあるので、10°の線と30分の長さは、試して調整する。

### 案B: 見上げる角度が低すぎる雲は、通知しない

- 雲のてっぺんの高さ（ひまわりで見積もった値）と、雲のふちまでの距離から、見上げる角度を計算する（アプリの方角ガイドと同じ計算）。
- 角度が **8° 未満**の雲は、通知しない。いまの「60kmより遠いと『見えるかもしれません』」の通知はやめる。
- ホームの画面には、そういう雲も残す。ただし文言は「遠くにあります（見えにくい雲）」とする。いまは、遠い雲も「見えています」と出る（10/30 16:40 の答えは、ホームの表示に対するもの）。
- 効く場面: 見えなかった4つは、すべて8°未満なので、案Bだけで全部外れる。
- 副作用: 無料の30kmと、プラスの90kmの範囲の意味が変わる。プラスの「90kmまで」は、「背が高い雲なら90kmまで」になる（高さ14kmで95km、12kmで82km）。プラスの画面の文言を直す必要がある（「90km先まで見張る」は、このままでも嘘ではない）。

### 案C: 「背の高い雲」の線を厳しくする

- てっぺんの温度を **-30℃ 以下**にする（いまは -20℃。-30〜-20℃ の約半分が外れる）。
- 高さの見積もりの下限（6km で切り上げ）をやめて、**見積もった高さが8km未満の雲は入道雲としない**。
- 小さすぎる塊（広さ **20km² 未満**）は通知しない（夏の積乱雲の核は5〜10km 四方で 25〜80km² なので、通りそう。ただし夏のデータで確かめる）。
- 効く場面: 見えなかった4つのうち、-23℃（広さ32km²）、-37℃（7km²）、-38℃（18km²）の3つは、この案でも外れる。-47℃（3.5km²）は広さで外れる。
- 副作用: 夏の、発達しはじめたばかりの小さな入道雲を見逃す。数字は夏の「見えた」で調整する。

### 案D: 判断に使った数字を残す（調整のため）

いまは、雲のデータは3日で消えるので、「見えなかった」の答えと、そのときの雲の性質を、あとから突き合わせられない（今回は、たまたま3日以内だった）。

- 通知を送るとき、判断に使った数字（てっぺんの温度、高さ、広さ、距離、見上げる角度、太陽の高さ、日照の判定の結果）を、member_server の通知の記録か新しいコレクション（notification_log）に残す。位置は丸めた値だけ。1年で消す（プライバシーポリシーの期間に合わせる）。
- 夏に「見えた」「見えなかった」が集まったときに、しきい値（8°、-30℃、20km² など）を、データで決められる。

### 案E（あとで）: 雷の活動度や、近くの山の高さを使う

- 冬の日本海側のしゅう雨は、雷の活動度が0だった。夏の背の高い雲では、雷の活動度が出ることが多いので、条件に足せる。ただし、育ちはじめの入道雲は雷がまだ出ないので、足すなら「てっぺんが -50℃ 以下」との「どちらか」にする。
- 山に隠れるか（国土地理院の標高データ）は、docs/検知の精度を上げるデータの比較.md の案6。見えなかった4つは、遠さで外れるので、後回し。

## 4. おすすめの進め方

1. **案B（角度）と案A（日照の判定）を先に入れる**。見えなかった4つは、案Bだけで全部外れ、案Aだけでも通知の3回は全部外れる。2つを入れると、どちらかが漏れても、もう一方が止める。入れたあと、過去の通知を新しいルールに通して、何件外れるかを数えて確かめる。
2. 案Cは、案A・Bを入れてしばらく使ってから、案Dで集めた数字を見て決める。先に案Cを入れると、夏のデータがないまま、見逃しが増えるかもしれない。
3. 案Dは、案A・Bといっしょに入れる（あとから調べられなくなるのを防ぐ）。

## 5. 決めてほしいこと

1. 見上げる角度の下限を **8°**（こぶし1つ弱。高さ10kmの雲なら69kmまで）にしてよいか。もっと厳しく10°（同55kmまで）にすることもできる。
2. 「60kmより遠い雲を『見えるかもしれません』と知らせる」のを、**やめてよいか**（ホームには残す）。
3. 太陽が低くて曇りを確かめられない時間は、**通知しない**でよいか（朝と夕方の通知が減る）。
4. 判断の数字を残す（案D）のを、プライバシーポリシーに書いたうえで入れてよいか。

## 6. まだ分からないこと

- 冬（秋）の日本海側のしゅう雨の雲は、4つしかデータがない。どれも「見えなかった」なので、「見えた」側の数字がない。夏の「見えた」が集まるまでは、しきい値は目安。
- 案Aの 10° は目安。曇りの日に曇りと判定できることは、見えなかった3回の通知で確かめた。晴れの日に晴れと判定できるかは、岩手の10/25〜11/1 のアメダス（見張る場所の20km以内の5地点）で、一部だけ確かめた。
  - 朝は、晴れた日（10/29、11/1）に、太陽が 13〜14° の 07:30 から、5地点中4〜5地点で日照があった。
  - 夕方は、晴れていても、太陽が 6〜8° まで下がると日照が 0〜2/5 に減る日があった（10/26、10/27、10/31）。山の影の可能性がある。
  - 最近の岩手は曇りの日が多く、晴れの日のデータが少ない（10/29 と 11/1 の朝くらい）。夏の晴れた日で、もう一度確かめる。
- 山や建物で見えない場合は、まだ考えに入っていない（案E）。

## 7. 調べた方法（やり直せるように）

- 見えなかった答え: Firestore の reports（4件）と、その cloudId の clouds。
- 雲のてっぺんの温度の分布: 本番の clouds 4,751個（3日分）。
- 太陽が低い時間: 岩手（北緯39.78°、東経141.13°）で、functions/modules/geo/sun_times.js の `isDaytime` を使って、日ごとに計算した。
- 日照の実測: アメダスの10分ごとの全国の観測（2026-11-01 と 11-02 の 06:00〜17:00）を、地点ごとの太陽の高さで分けて数えた。
- 赤外画像との比較: 2026-11-01 12:00 の、アメダス約580地点とひまわりの赤外画像。
